# Knowledge Graph Guide: Platform V2

This document details the architectural layout, entity schemas, relationship vocabulary, and compiler details for the ValidoHub Knowledge Graph (introduced in Platform V2).

---

## 1. Directory Structure

All Knowledge Graph files are organized under the `knowledge/` root directory at the project root:

```
knowledge/
  ├── entity-schema.json          # Formal JSON Schema for entities
  ├── relationship-schema.json    # Formal JSON Schema for relationships
  ├── relationships.json          # Central relationship index file
  ├── compiled-graph.json         # Graph compiler build artifact output
  └── entities/                   # Decoupled entity collection directories
      ├── authority/              # e.g., bzst.json, aeat.json, bcb.json
      ├── banking-standard/       # e.g., iban.json, bic.json
      ├── country/                # e.g., germany.json, brazil.json, spain.json
      ├── identifier/             # e.g., steuer-id.json, pesel.json, cpf.json
      ├── payment-system/         # e.g., pix.json, sepa.json, blik.json
      ├── tool/                   # e.g., iban-validator.json
      └── workbench/              # e.g., pesel-validator.json, nip-validator.json
```

---

## 2. Namespace & Entity ID Conventions

Every entity in the graph must have a globally unique, lowercase, namespaced ID using the format:

$$\text{id} = \text{type} : \text{slug}$$

- **Format:** `type:slug` (e.g. `country:germany`, `identifier:steuer-id`, `authority:bzst`, `workbench:pesel-validator`).
- **File Name Mapping:** The file name must match the slug (e.g., `knowledge/entities/country/germany.json` holds the entity `country:germany`). The Graph Compiler enforces this matching as a strict integrity check.

---

## 3. Profile Content vs. Graph Entities

ValidoHub decouples content presentation from semantic identity:

1. **Country Profiles (`countries/data/*.json`)**:
   - Contains presentation-ready Country Hub markdown copy, checklists, validation rules, localized formatting examples, and code snippets.
2. **Knowledge Entities (`knowledge/entities/**/*.json`)**:
   - Contains canonical semantic metadata: ID, type, name, aliases, short definition, and stable reference URLs.
3. **Relationships (`knowledge/relationships.json`)**:
   - Explicitly links entities together semantically without polluting presentation templates.

---

## 4. Controlled Relationship Vocabulary

Every relationship declared in `knowledge/relationships.json` must belong to the controlled vocabulary described below:

| Relationship Verb | Source Type(s) | Target Type(s) | Inverse Verb (Autogenerated) | Description |
| :--- | :--- | :--- | :--- | :--- |
| `USES_IDENTIFIER` | `country` | `identifier` | `USED_BY_COUNTRY` | A country uses this format for tax/identity verification. |
| `SUPPORTS_PAYMENT_SYSTEM` | `country` | `payment-system` | `SUPPORTED_BY_COUNTRY` | A country supports this domestic payment infrastructure. |
| `PARTICIPATES_IN` | `country` | `banking-standard` | `PARTICIPATED_IN_BY_COUNTRY` | A country participates in this banking standard (e.g., IBAN). |
| `GOVERNED_BY` | `identifier`, `payment-system`, `banking-standard` | `authority` | `GOVERNS_ENTITY` | This entity is governed/regulated by the target authority. |
| `VALIDATES` | `workbench`, `tool` | `identifier`, `banking-standard` | `VALIDATED_BY_ENTITY` | This workbench or developer tool validates the given identifier. |
| `IMPLEMENTS` | `tool` | `banking-standard` | `IMPLEMENTED_BY_ENTITY` | This tool implements the given banking standard format. |
| `PUBLISHES_REFERENCE_FOR` | `authority` | `country`, `identifier`, `payment-system` | `REFERENCED_BY_AUTHORITY` | This authority publishes reference specifications for the target. |

## 5. Source & Evidence Metadata Schema

Non-trivial relationships can optionally document verification evidence using the `evidence` object:

```json
{
  "source": "identifier:steuer-id",
  "type": "GOVERNED_BY",
  "target": "authority:bzst",
  "evidence": {
    "sourceUrl": "https://www.bzst.de/DE/Steuern_National/Steueridentifikationsnummer/",
    "authority": "Federal Central Tax Office",
    "verifiedAt": "2026-07-12T18:00:00Z",
    "confidence": 1.0,
    "note": "Governing ministry link confirmed."
  }
}
```

## 6. Graph Compiler Validation Rules

The Graph Compiler (`scripts/compile-countries-registry.mjs`) validates the following constraints during every build:

1. **Referential Integrity (Error):** Fails if any relationship's `source` or `target` ID does not exist in the loaded entities.
2. **Duplicate Global IDs (Error):** Fails if two entities share the same global namespaced ID.
3. **Directed Cycle Check (Error):** Audits relationships for prohibited cyclical dependency loops.
4. **Orphan warnings (Warning):** Logs a warning if an entity has no relationships, but does not block compilation.

---

## 7. How Future Tools & Standards Join the Graph

When adding a new tool (e.g. `phone-validator`) or standard (e.g. `cldr`):

1. **Create Entity File:** Add the definition under `knowledge/entities/tool/phone-validator.json` or `knowledge/entities/banking-standard/cldr.json`.
2. **Register Relationships:** Add the connection in `knowledge/relationships.json` (e.g., `tool:phone-validator --VALIDATES--> identifier:phone-number`).
3. **Run compiler:** Execute `node scripts/compile-countries-registry.mjs` to validate and compile.
