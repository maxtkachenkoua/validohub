# Generic Workbench Gold Standard

This document is mandatory product memory for every ValidoHub generic, non-country tool.

Generic tools are not secondary utilities. They must be premium product workbenches that match the quality, visual hierarchy, interaction richness, and depth of the best Poland and Brazil national instruments.

Highest priority for country-scoped tools: every country tool must aim to become a Pix/CURP-level best-in-world page to the maximum extent its format allows. This overrides any older interpretation that a generated country route, generic factory shell, or shared overlay can be considered sufficient. If the format has deeper browser-checkable structure, the actual route must expose that depth with bespoke interaction, local logic, parser/anatomy, generation, replay/debugging, safe fixtures, developer output, source links, traps, and official-boundary clarity.

## Product Standard

Every current and future generic tool must be built as if it is intended to be the best tool of its kind on the internet.

The benchmark is not "working" or "clean." The benchmark is:

- Poland country workbenches for density, validation depth, advanced analysis, result cards, local conventions, diagnostics, and developer-grade explainability.
- Brazil country workbenches for visual confidence, branded workbench presence, vivid but controlled identity, rich tool headers, and premium interaction polish.
- The strongest competing public tools on the internet for the same task, then exceed their functional depth. If a competitor offers X meaningful capabilities, ValidoHub should aim for at least X plus a richer analysis layer, and often X times 2 where the domain supports it.

For country-scoped and local-market tools, the same best-in-world ambition applies only after the tool earns a place in the product. Tool inventory is not a quota. Some countries may deserve hundreds of visible tools because the market has many useful public/spec-backed workflows; others may deserve only a few. Do not promote weak generated artifacts to maintain visual density. First decide whether the tool has real developer value, then decide how deep it should become.

## Non-Negotiable UX Rules

Each generic workbench must be tool-first. The usable instrument is the first meaningful screen, not documentation, marketing copy, or a thin form.

Each generic workbench must include, where applicable:

- A branded, tool-specific header with precise copy and local trust/privacy badges.
- Mode-specific presets and samples that succeed in the current mode by default.
- Presets for valid, invalid, edge-case, real-world, and developer/debug scenarios.
- Browser-only/offline execution whenever possible.
- A validation or processing pipeline visual with states that never collapse into text runs.
- Premium result cards with compact typography, no cramped inline labels, and copy actions on values users actually need.
- Advanced analysis expanded by default when it teaches or verifies the result.
- Field, byte, token, claim, component, or step breakdowns appropriate to the domain.
- Interactive exploration panels, not static dumps, wherever the data structure allows it.
- Quality notes, repair suggestions, warnings, limitations, and privacy/network boundary copy.
- Developer API previews that match the active action or mode, never stale generic snippets.
- Copy, download, history, sample, and batch flows where they make the workbench meaningfully better.
- Local result JSON or audit export for developer workflows where useful.
- Per-tool documentation and descriptions. Never use repeated generic copy.

## Visual Rules

Generic workbenches must visually follow the premium country workbench system:

- Compact, premium card typography.
- Dense but readable information hierarchy.
- Branded headers and tool identity cues.
- Polished buttons, tabs, chips, selectors, timelines, code blocks, and explorer rows.
- No native browser-looking controls in premium surfaces.
- No raw unstyled advanced sections.
- No floating status words, collapsed timeline labels, overlapping result text, or single-line metric collisions.
- No card-inside-card clutter unless the component is a real nested tool surface.
- Advanced panels and result areas must look intentional at desktop and mobile widths.

If a generic tool emits legacy shared fragments, CSS must explicitly support those fragments until the markup is modernized.

## Functional Depth

Generic tools must be enriched beyond basic conversion/validation:

- Encoding tools should include variants, normalization, padding, URL-safe modes, bytes, chunks, previews, files, batch, repair suggestions, and examples.
- JSON/JWT-like tools should include tree explorers, search, path/pointer copy, syntax and semantic diagnostics, structured downloads, claim or node analysis, and safe samples.
- URL tools should include component parsing, query tools, reserved/unsafe character analysis, normalization, sorting, repair, and percent-byte inspection.
- Hash tools should include multiple algorithms where relevant, file hashing, HMAC or keyed hashing when appropriate, checksum comparison, batch, encoding inputs, and security notes.
- Text tools should include diff modes, normalization, casing locale notes, slug rules, Unicode/codepoint analysis, batch options, and copyable outputs.
- Identifier-like generic tools should include normalization, checksum/math explanation, masked output, generated safe fixtures, batch validation, and audit JSON.

The exact features depend on the domain, but the standard is always exploration and analysis, not a single output box.

## Best-In-World Format Lab Rule

For identifier, payment, banking, tax, registry, invoice, postal, phone, and other structured local-market formats, a finished premium tool must be treated as an interactive specification laboratory, not a nicer validator.

The required benchmark is: implement everything that the public format, public specification, official registry documentation, or well-established open algorithm allows ValidoHub to test locally in the browser. Then compare against the strongest public competitors for the same workflow and exceed them with richer diagnostics, safer fixtures, clearer developer handoff output, and stricter official-boundary explanations.

The retention target is one-stop usefulness: a developer should be able to arrive once, test the format deeply, learn the rules while testing, copy or export the useful output, follow official source links, understand what still requires a live authority/system, and have no reason to return to weaker competitor tools for that workflow.

A finished structured-format workbench must include every applicable capability the domain supports:

- Format, length, charset, punctuation, country/system support, and reserved/forbidden value checks.
- Checksum, control digit, CRC, MOD-97, Luhn, ISO 7064, weighted-sum, or other public algorithm replay with expected/provided values and step-by-step evidence.
- Field anatomy and parser output: date, century, age estimate, gender marker, region, bank, branch, account, company root, establishment, tax/entity type, payment tag, currency, amount, reference, QR payload, or other public segments.
- Normalized, display, masked, electronic/raw, and storage-safe forms.
- Safe fixture generation where the format allows it: valid, invalid checksum, wrong length, bad prefix/country, malformed payload, edge date, grouped/display, and masked examples.
- Batch validation and import/debug workflows where developers commonly paste CSV, JSON, lists, or exported values.
- Copy-ready developer output: parsed JSON, API preview, audit export, generated payload, QR/SVG/PNG/download where relevant, and current-result copy actions.
- Concrete integration traps for that exact workflow: leading zeros, punctuation vs storage, stale registry tables, checksum vs official existence, dynamic vs static payment boundaries, decimal separators, privacy/logging, masked-output handling, and known false-positive cases.
- Official/live-system boundary notes that clearly state what ValidoHub proves locally and what still requires a registry, bank, tax authority, payment network, or official API.

Do not call a workbench finished when it only returns `valid` or `invalid` for a regex-like shape while the public format supports deeper parsing, checksum replay, fixture generation, or developer diagnostics. If the public rules are limited, the tool must stay honest and visibly limited instead of inventing unsupported semantics.

Every tool should feel like it belongs to the same ValidoHub product: a consistent premium shell, compact hero, input/samples/actions, immediate result, breakdown, traps, official boundary, developer output, source links, copy/download states, and documentation hierarchy. This consistency is the baseline user contract.

That baseline must never become a ceiling. For Gold/local flagship tools, use common shell for consistency and bespoke depth for excellence. When a format has more public structure or interaction potential than the shared shell can express, the local tool page may add any browser-only component, workflow, action, layout, local JavaScript, CSS, parser, analyzer, generator, or visual explorer needed to become the best tool in the world for that format.

Allowed and expected tool-specific enrichment includes local JavaScript analyzers, parsers, checksum/CRC engines, QR/payload generators, fixture generators, batch debuggers, anatomy explorers, interactive trees, custom CSS/layout, download/export actions, source links, mode switchers, repair/lint suggestions, registry panels, source-backed documentation panels, local implementation snippets, and any other domain-specific UX that helps users test, understand, generate, debug, or integrate the format. Do not flatten a rich local format into a generic factory analyzer just because the shared shell cannot express it yet.

For Gold/local flagship work, maintain an internal AI implementation log in `docs/ai/gold-tools/` or the current documented successor location. The log is part of the Definition of Done, not optional notes. It should explain source decisions, official boundaries, competitor gaps, implementation choices, test fixtures, QA commands, browser observations, and remaining risks so future AI sessions can continue or audit the work without relying on chat memory.

Gold is not a migration label. Do not describe a route-bound overlay, generic country-suite enhancement, or partially improved analyzer as finished Gold. If the page is called Gold, the user-facing page must already be bespoke maximum-quality for its workflow: custom browser logic and layout where needed, every locally checkable format capability, source-backed explanations, safe fixtures, copy/export output, integration traps, official-boundary notes, and visual polish at the Pix/CURP/Spain ID bar. Shared overlays may help inventory and triage, but they are scaffolding until the actual page is promoted to a real bespoke Gold tool.

Flagship examples:

- PESEL-level identifier tools decode anatomy, dates/centuries, age/gender markers where public, checksum math, edge samples, and official identity boundaries.
- Pix-level payment tools are the elite reference for a bespoke Gold tool: one connected browser lab where the same input drives validation, generation, parsing, QR/payload output, field-tree exploration, checksum/CRC replay, safe fixtures, implementation lint, official source links, developer JSON, and workflow-specific traps. Future Gold tools should copy this product model when their domain supports it: visible Gold identity, no duplicate sandbox, immediate input-driven evidence, rich debugging before documentation, and responsive layout that never lets long payloads, tables, buttons, or generated artifacts create page-level horizontal overflow.
- IBAN-level banking tools validate country support, length, BBAN structure, MOD-97, formatted/electronic forms, local bank/branch/account fields where public, generation, and account-existence boundaries.

## Pix-Derived Bespoke Gold Layout Rules

Brazil Pix is the current accepted elite implementation for a bespoke Gold tool. Future flagship tools must preserve these lessons instead of re-learning them tool by tool:

- Build one connected lab, not a generic base tool plus a duplicate Gold sandbox lower on the page. Presets, input, generator fields, analyzer, parser, debugger, output, developer JSON, sources, and traps must all read from the same current state.
- Country route-bound rich labs must mount as the primary workbench in the route host, not as an afterthought below the generic factory page. If a shared runtime is used across many routes, it must still present the useful tool first: source links, samples, input, local evidence, anatomy, replay, lint, traps, boundary, and developer snapshot in one connected flow.
- Put the Gold evidence strip and primary diagnostics near the workbench controls, before long documentation. Users should understand the result and debugging evidence without hunting at the bottom of the page.
- Long payloads, identifiers, JSON, tables, QR outputs, action rows, and generated artifacts must be contained by local wrapping, truncation, or local scroll. Page-level horizontal overflow is a blocker.
- Tables inside analysis cards must visually fill the card width. If a table contains long raw values, constrain columns with `table-layout: fixed`, local ellipsis/wrap, or scroll inside the table wrapper; do not leave unused blank space to the right and do not let content widen the page.
- Tree/explorer and table views should complement each other: a compact visual anatomy view for reading, plus a full-width table for offsets, tags, raw segments, lengths, values, and diff/debug evidence.
- Integration traps are a compact developer time-saver, not a hero block. Keep typography smaller and softer than primary result text, use concrete workflow-specific bullets, and avoid repeated generic filler.
- Official sources and boundary panels should sit near the debugging surface, use compact readable typography, and explicitly distinguish local browser evidence from official existence, ownership, settlement, account status, registry status, or live authority checks.
- Developer snapshots belong after the human debugging panels and before related tools/docs, so they are available for export without interrupting the primary reading flow.

## CURP-Derived Interaction And Form Layout Rules

Mexico CURP is the accepted bespoke identifier-lab layout reference for dense local ID tools. Future identifier, tax-ID, registry-ID, banking-ID, and country-scoped Gold tools must preserve these fixes:

- The primary lab must flow as one full-width work surface: sample/actions/input/generator first, then the full-width result/evidence area below. Avoid side-by-side layouts when either side can create tall empty columns, clipped controls, or page-level overflow.
- Dense generator forms must use explicit balanced responsive grids. Five-field generators should use a stable `3 + 2` or similarly balanced layout, not a `4 + 1` row that leaves a lonely field and clipped selects.
- Use native date pickers or a clear date control whenever the generated fixture depends on a calendar date. Do not make users type dates into a plain text-looking field when the browser can provide a safer picker.
- Segmented controls are preferred for small closed choices such as sex/gender markers, modes, and yes/no options. They must look intentional, stay inside their container, and not use raw native select menus for two-option premium controls.
- Buttons, chips, links, and segmented options must have visible hover/focus/active states, but those states must not move the layout. Avoid hover `transform: translateY(...)` in dense workbench controls. Use contained border/background/inset-shadow changes instead.
- Focus rings must be visible and contained inside tight cards or button rows when an external ring would overlap adjacent frames.
- Action rows must have deliberate top spacing from the card above. Buttons must never visually touch or climb into the generator/input card on hover or focus.
- Every Gold tool with a Developer Snapshot must expose a `Copy developer JSON` action near that snapshot, not only in the primary action row. Clipboard behavior needs visible feedback and a fallback for browsers where `navigator.clipboard` is unavailable.
- Long normalized IDs, masked values, JSON strings, official-boundary copy, and generated payloads must wrap or scroll locally. No field, card, pre block, table, or button row may widen the whole page.
- When a bespoke Gold tool is hosted by a country-suite route, generated HTML must be route-postprocessed to load that tool's bespoke runtime and remove the shared `gold-tools-lab.js` overlay on that route. Do not rely only on the YAML `algorithmId` if the country materializer preserves the parent suite algorithm. The route may keep the country-suite factory scripts, but the bespoke runtime must own the visible lab and replace the static host.

## Mode Integrity

Every mode must be coherent end to end:

- A decoder must not show encoder-first presets.
- A validator must not show generator-first history labels.
- API snippets must use the active operation.
- Badges, messages, result labels, downloads, filenames, and copy actions must match the selected action.
- The first available preset must demonstrate success unless it is explicitly labeled as an invalid/error sample.
- Error samples must be intentional, labeled, and visually polished.

## Localization

All localization work must cover every supported language and every visible user-facing surface affected by the tool:

- Titles.
- Descriptions.
- Preset labels.
- Button labels.
- Result labels.
- Warnings.
- Repair suggestions.
- Documentation sections.
- Empty states.
- Advanced analysis labels.

Do not localize only page titles.

## Future Tool Rule

Any new generic instrument must start from this gold standard. It is not acceptable to ship a generic form and plan to enrich it later unless the task explicitly says to build a temporary scaffold.

## New Generic Instrument Contract

When adding a new global tool under `/{locale}/tools/{tool-slug}/`, do not start from the minimum Engine-generated form. Start from the premium workbench contract:

The `/en/tools/` directory is mandatory for global-tool discovery. Follow `docs/product/TOOLS_PORTAL_SPEC.md` in addition to this gold standard whenever adding, renaming, or hardening a global tool.

- Define the tool-specific product spec and registry entry before or alongside implementation.
- Choose a deterministic neutral visual theme, mark, chips, and header copy; never use country flag colors for a country-neutral tool.
- Ship a success-first default preset for every primary mode. The first available preset must succeed in the selected mode.
- Ship at least one invalid/error preset where validation is part of the tool domain, and make the error result visually premium.
- Place the primary result block immediately after the input/action area. Advanced analysis must follow the result, not hide the result.
- Include a validation/processing pipeline, premium result cards, field/component/byte/token breakdown, quality notes, and developer JSON or API preview where useful.
- Include copy/download behavior for the values developers actually need, not only the raw textarea output.
- Browser-verify first load, first preset, primary success, invalid/error, mobile layout, and advanced analysis before calling the tool complete.
- If a competing public tool has a meaningful capability, ValidoHub should match it and add a richer local analysis layer.
- Global tools must compete on domain depth, not only presentation. JSON needs repair/schema/path/flatten/secret-scan intelligence; JWT needs claim timeline, security checklist, and verification-boundary explanation; Base64 needs byte/data-URI/MIME/canonicalization inspection; URL tools need full URL parsing, query tables, canonical output, redirect/credential/UTM/security hints; UUID and IBAN tools need generation plus validation/debug replay where the domain allows it.
- `npm run audit:global-premium -- --base <local-url>` is the required fast-loop audit for global tool work. It must pass before a global tool hardening task is called done. A full `npm run build` remains the release gate, but global-only development should not wait on full-site materialization when targeted generated assets and browser audits are enough for iteration.

When upgrading existing generic tools, audit the whole user flow:

1. First load.
2. First preset.
3. Primary successful run.
4. Primary invalid/error run.
5. Advanced analysis.
6. Copy/download/history.
7. Mobile layout.
8. Developer snippets.
9. Documentation and related tools.

If any of these looks weaker than the Poland/Brazil workbench baseline, keep iterating.

## IBAN Global And Country Rule

IBAN is both a global finance standard and a country-specific banking structure. Do not treat every IBAN page as interchangeable SEO copy.

- Keep one global `IBAN Validator` under `/{locale}/tools/iban-validator/` as the universal entry point.
- The global tool must detect the country, validate ISO shape, country length, MOD-97, grouping, masking, and ownership-boundary notes.
- If ValidoHub has a supported country hub and the country has meaningful local IBAN/BBAN structure, provide a country-specific IBAN workbench.
- Country-specific IBAN pages must add real local value: BBAN field map, bank/branch/account slicing, domestic check digits where available, local examples, common mistakes, payment/SEPA notes where relevant, and clear official lookup boundaries.
- Country-specific IBAN pages must not be thin duplicates of the global page. If a country has no meaningful local rules or demand, leave it as a detected profile in the global tool until the product case is strong.
- The global result should point users to the deeper country page when one exists.
- Country pages must reject or clearly flag wrong-country IBANs rather than silently validating them as generic IBANs.
